# Setup and infrastructure

Start with selected capability entries and the execution surface. Discover recommended plugins in the available catalog, explain their purpose, and guide installation and account authorization for selected services. Use connected tools first, provider APIs/CLIs next, and browser/computer tools for dashboard-only setup and verification.

Core capabilities are repository/CI access through GitHub, shell with Git/Node/pnpm, browser or computer control for applicable runtime flows, Fallow, and Cloudflare's security-audit skill. Cloudflare/Wrangler is required for Cloudflare apps and services. Neon, Stripe, RevenueCat, Resend, Sentry, PostHog and Vercel are conditional. Figma and communication/project-management plugins depend on the user's workflow. Retrieve current official installation guidance and discover catalog availability; registry tool names describe capabilities, not guaranteed listings.

Verify CLI versions and authenticated account identity with read-only commands. Access fields describe required capabilities; derive current exact provider permission names from official documentation. Prefer scoped account/project access. Plugin OAuth does not automatically authorize local CLIs or CI runners.

For new repositories, pin the CLI version matching `cliVersion` in the registry. Inspect `pnpm dlx anhedral@<version> new <directory> <selected-flags> --dry-run --json`, then generate into an empty destination. Compare its requirements with the bundled registry; another CLI version needs its actual plan and documented differences. Commit the lockfile and inspect README, AGENTS, `anhedral.standard.json` and `anhedral.setup.json`. Bootstrap uses `shadcn@latest`, so CLI pinning alone does not make different generation dates identical. Existing applications require deliberate changes; the CLI has no `add` or migration command. Run `anhedral doctor <directory> --json` to check local requirements and CLI compatibility without writes; its result never verifies provider identity, permissions or production readiness.

During plugin development, unpublished CLI changes require the local checkout: `pnpm build`, then `node dist/bin.js new <directory> <selected-flags> --dry-run --json`. Do not expect published npm versions to contain unshipped setup fields. Verify the returned plan's schema and capabilities as well as its version before relying on it.

Provision selected resources in client-owned accounts with separate environments. Confirm existing resources before creating duplicates. Configure identifiers/bindings and keep actual secrets in ignored local files and provider secret stores. Use separate database migration/runtime roles. For Neon, verify Hyperdrive connectivity and disable query caching for correctness-sensitive data. Keep R2 buckets private and authorize file operations through Workers. For Basin/Pipelines, verify service plan eligibility and obtain the managed Workers Pipelines application's `Pipelines Setup` grant only when required for the selected sink. Keep ingestion private unless the product needs an authorized public endpoint.

For domain/mail setup, follow the current standard: GoDaddy registration/broker access and Cloudflare nameservers/DNS, inbound Email Routing and default outbound Cloudflare Email Sending, or explicitly selected Resend. Verify current sending eligibility, sender authentication and bindings/credentials. The current CLI's `resend` flag generates only the Resend integration; Cloudflare sending and domain configuration need separate setup. Never publish private forwarding destinations or treat email routing as a mailbox migration.

Purchase in the client's registrar account, then add a zone in the client's Cloudflare account. Review existing DNS records before changing the registrar's nameservers and verify the zone becomes active. Client ownership includes registration, renewal billing and recovery access; configuring Cloudflare DNS does not transfer registration. Follow current Cloudflare onboarding guidance for DNSSEC and mail-record preservation when applicable.

Configure selected auth origins, webhooks and reviewed migrations. Define retries, idempotency and failure handling for background work, and entitlement authority for billing. RevenueCat, Sentry and local-data boundaries need actual platform SDK/adapters and behavior.

Before paid activation, required terms or broader grants, describe the exact account, action, scope and cost for any authorization still missing. Record unavailable services, fallback and next action, and continue independent work. Setup completion requires account/scope verification, confirmed configuration, server-side secrets, applicable migration evidence and an explicit list of unfinished product work.
